# 第2页 · 上节回顾

## 要点卡片

### ① 线程安全

* 多线程并发访问同一对象，**无论调度顺序如何，结果始终正确**
* 数据竞争（Data Race）：读-改-写三步被打断，结果错乱且不可复现

### ② 同步互斥机制

* 互斥锁家族：mutex / recursive / timed / shared
* 信号量家族：counting / binary
* 原子家族：atomic\_flag / atomic
* 辅助工具：lock\_guard / unique\_lock / scoped\_lock

### ③ 四方案粗糙测试结论

* 单线程：atomic 最快，mutex 有锁开销
* 多线程：atomic 领先，mutex 随线程数增加竞争加剧
* shared\_mutex：读多写少优势明显，写多反而不如 mutex
* CAS 循环：高竞争下可能退化为自旋，需谨慎

# 第3页 · 本节提要

## 两种实现方案 + 性能预告

### 本节要解决的两个问题

* **怎么实现**：自旋锁有哪两条技术路线？
* **怎么选型**：跨平台、高竞争下，谁更可靠、谁更快？

### 方案一：POSIX 自旋锁

* 基于 `pthread_spinlock_t`，系统级实现
* 优点：接口标准、开箱即用
* 隐患：**跨平台行为不一致**，需逐平台验证

### 方案二：atomic\_flag 自旋锁

* 基于 C++ 原子操作，纯用户态实现
* 优点：行为可控、可深度优化
* 隐患：需自己处理**指令级优化**与**抢占问题**

### 性能测试结果预告

* `pthread_spinlock` ≈ `atomic_flag`，两者差距极小
* **多线程高竞争下，综合性能均不如 `std::mutex`**
* 结论先行：自旋锁是"特定场景的利器"，不是"万能钥匙"

# 第4页 · 方案一：POSIX 自旋锁

## pthread\_spinlock 特性

### 核心机制

* **抢锁失败 → 反复检查**：不进入睡眠，持续轮询锁状态
* **不主动放弃 CPU**：自旋期间占用核心，等待期间不切换线程

### 适用前提

* 锁持有时间**极短**（微秒级）
* 临界区**无阻塞调用**（无 IO、无 sleep、无系统调用）

### 跨平台行为对比表

| **平台**      | **抢锁失败行为**  | **是否公平** | **备注**             |
| ----------- | ----------- | -------- | ------------------ |
| **Linux**   | 自旋 + 有限退避   | 非公平      | 高竞争下可能退化为 futex 睡眠 |
| **NetBSD**  | 纯自旋         | 非公平      | 无退避，极端依赖临界区长度      |
| **FreeBSD** | 自旋 + 自适应退避  | 非公平      | 行为接近 Linux，实现细节不同  |
| **macOS**   | 自旋 + 系统调度介入 | 非公平      | 高竞争下可能触发调度器干预      |

### 关键结论

* 四平台**均非公平**，但**退避策略各不相同**
* 同一份代码，换平台后**性能与行为可能天差地别**
* 跨平台项目：**不要假设 pthread\_spinlock 行为一致**

> 标准接口 ≠ 标准行为。跨平台，先测再信。

# 第5页 · 方案二：atomic\_flag 自旋锁

## 原理图解

```
       外层抢锁（test_and_set）          内层观察（只读不写）
   ┌──────────────────────┐      ┌──────────────────────┐
   │  while(flag.test_and_set) │      │  while(flag.test())      │
   │  {  // 抢锁失败        │      │  {  // 只读观察        │
   │     // 进入内层观察    │ ───▶ │     // 不写，减少缓存抖动 │
   │  }                    │      │  }                      │
   └──────────────────────┘      └──────────────────────┘
```

### 核心代码（含中文注释）

```cpp
#include <atomic>

class SpinLock {
    std::atomic_flag flag = ATOMIC_FLAG_INIT;  // 初始为清除态（未锁定）

public:
    void lock() {
        // 外层：test_and_set 原子地"置位并返回旧值"
        // 若旧值为 false（未锁定）→ 抢锁成功，跳出循环
        // 若旧值为 true（已锁定）→ 抢锁失败，进入内层
        while (flag.test_and_set(std::memory_order_acquire)) {
            // 内层：只读观察，不写内存
            // 避免反复 test_and_set 造成缓存行抖动（cache line bouncing）
            while (flag.test(std::memory_order_relaxed)) {
                // 空转等待，可在此插入 pause / __yield 指令
            }
        }
    }

    void unlock() {
        flag.clear(std::memory_order_release);  // 清除锁标志，释放临界区
    }
};
```

### 设计要点

* **外层抢锁**：`test_and_set` 是"读-改-写"原子操作，负责真正抢锁
* **内层观察**：`test()` 只读不写，**不污染缓存行**，降低多核竞争开销
* **内存序**：acquire/release 保证临界区数据同步，relaxed 用于纯观察

> 内层只读不写，是自旋锁性能的关键——少一次写，少一次缓存抖动。

# 第6页 · 指令优化

## x86 pause 指令

### 四条作用要点卡片

**① 降低功耗**

* 自旋等待时让 CPU 进入低功耗微状态，减少发热与耗电

**② 减少流水线冲突**

* 避免自旋循环中的内存访问打乱指令流水线

**③ 缓解缓存竞争**

* 降低对共享缓存行的争抢压力，提升多核吞吐

**④ 提升公平性**

* 让出部分执行资源，给其他线程更多抢锁机会

```cpp
// x86 自旋等待优化
while (flag.test(std::memory_order_relaxed)) {
    _mm_pause();  // x86 专用：暂停流水线，降低功耗与竞争
}
```

### ARM \_\_yield 对应说明

* ARM 平台对应指令：`__yield()`（内建函数）
* 作用与 x86 `pause` 等价：**提示 CPU 当前处于自旋等待**
* 效果：降低功耗、减少流水线冲突、缓解缓存竞争
* 跨平台写法：用宏或 `#ifdef` 按架构分发

```cpp
#if defined(__x86_64__)
    #define SPIN_PAUSE() _mm_pause()
#elif defined(__aarch64__)
    #define SPIN_PAUSE() __yield()
#else
    #define SPIN_PAUSE() ((void)0)
#endif
```

> 一条指令，四重收益。跨平台自旋锁，指令优化是必修课。

# 第7页 · 锁持有者抢占

## 场景时序图（A/B/C 三线程 × 双CPU）

```
CPU0:  A[持锁] ──被抢占──▶ A[睡眠] ──────▶ A[唤醒] ──▶ A[继续]
CPU1:  B[自旋等待] ──────▶ B[自旋等待] ──▶ B[自旋等待] ──▶ B[抢锁]
       C[排队等待]                          C[排队等待]
```

* **A 持锁期间被系统抢占**（时间片耗尽或更高优先级线程介入）
* B、C 在另一核上**空转自旋**，白白烧 CPU
* A 被唤醒前，B、C 只能干等——**锁被"冻结"了**

### 后果清单（6条）

1. **CPU 空转浪费**：等待线程持续自旋，占用核心算力
2. **功耗飙升**：多核空转导致发热与耗电激增
3. **延迟不可控**：持锁者被抢占，临界区完成时间被无限拉长
4. **优先级反转**：低优先级持锁者抢占高优先级等待者
5. **吞吐下降**：锁被冻结期间，整个临界区吞吐归零
6. **死锁风险**：持锁者被抢占后依赖的线程无法推进，可能连锁卡死

> 自旋锁最怕的不是竞争，而是"持锁者被抢走"——抢占是自旋锁的天敌。

# 第8页 · 适用场景判断

## 适合场景（6条）

1. **临界区极短**：微秒级操作，自旋开销小于线程切换
2. **低竞争**：锁冲突少，自旋等待时间可忽略
3. **多核机器**：有富余核心供自旋，不阻塞其他任务
4. **实时性敏感**：避免线程切换的调度延迟
5. **不可睡眠上下文**：中断处理、内核路径等禁止阻塞
6. **高频短锁**：如引用计数、标志位更新等热点操作

## 不适合场景（8条）

1. **临界区较长**：自旋时间超过线程切换成本
2. **高竞争**：大量线程争抢，自旋空转浪费严重
3. **单核机器**：自旋期间无其他核心可推进，纯浪费
4. **持锁者可能被抢占**：实时/分时系统风险高
5. **临界区含阻塞调用**：IO、sleep、系统调用会放大风险
6. **优先级反转敏感**：实时系统不可接受
7. **功耗受限**：移动端、嵌入式等对功耗敏感
8. **可扩展性要求高**：线程数增长时自旋锁性能急剧恶化

> 一句话判断：临界区短、竞争低、多核、可自旋——用；否则，用 mutex。

# 第9页 · 常见坑警示

## 8个编号警示卡片

**① 抢占（Preemption）**

* 持锁者被系统抢占，等待者空转烧 CPU

**② 优先级反转**

* 低优先级持锁者阻塞高优先级等待者

**③ 重复加锁**

* 自旋锁**不可重入**，同一线程二次 lock 直接死锁

**④ 不公平**

* 非公平调度，等待线程可能长期饿死

**⑤ 缓存抖动**

* 反复 test\_and\_set 写操作引发 cache line bouncing

**⑥ 生命周期**

* 锁对象被提前销毁，悬垂引用导致未定义行为

**⑦ 初始化错误**

* 忘记 `ATOMIC_FLAG_INIT` 或未正确初始化，行为未定义

**⑧ 异常未解锁**

* 临界区抛异常导致锁未释放，后续线程永久自旋

> 八个坑，个个致命。自旋锁是"高手玩具"——用错一次，线上事故。

# 第10页 · 自旋锁 vs std::mutex

## 五维度对比表

| **维度**   | **自旋锁**      | **std::mutex** |
| -------- | ------------ | -------------- |
| **等待极短** | ✅ 优势明显，无切换开销 | ❌ 切换成本高        |
| **被抢占**  | ❌ 持锁者被抢占则灾难  | ✅ 内核会调度等待者     |
| **高竞争**  | ❌ 空转烧 CPU    | ✅ 等待者睡眠，省资源    |
| **可阻塞**  | ❌ 临界区不可阻塞    | ✅ 可安全阻塞        |
| **功耗**   | ❌ 自旋持续耗电     | ✅ 睡眠等待，功耗低     |

### 选型结论

* **等待极短 + 低竞争** → 自旋锁胜出
* **高竞争 / 可阻塞 / 功耗敏感** → std::mutex 更稳

> 自旋锁赢在"快"，mutex 赢在"稳"——没有绝对优劣，只有场景适配。

# 第11页 · 性能测试结果

## 实测结论

### ① pthread\_spinlock ≈ atomic\_flag

* 两者性能**几乎持平**，差距在误差范围内
* 说明：用户态自旋锁的优化空间已接近系统实现

### ② 多线程下综合性能不如 std::mutex

* 线程数增加 → 竞争加剧 → 自旋空转成本飙升
* mutex 让等待线程睡眠，**高竞争下反而更高效**

### ③ 关键启示

* 自旋锁的"快"只在**低竞争、短临界区**成立
* 高竞争场景，自旋锁的省切换优势被空转成本抵消

> 数据说话：自旋锁不是更快，而是"在特定场景下更快"。

# 第12页 · 总结

## 本节核心结论

### ① 实现方案

* 两条路线：**POSIX 自旋锁** 与 **atomic\_flag 自旋锁**
* 性能相当，但 atomic\_flag 行为可控、可深度优化

### ② 跨平台选择

* pthread\_spinlock **四平台行为不一致**，跨平台需逐平台验证
* atomic\_flag 基于标准原子操作，**行为可预期**

### ③ 性能结论

* 低竞争、短临界区：自旋锁胜出
* 高竞争、可阻塞、功耗敏感：**std::mutex 更优**

### ④ 使用铁律

* 临界区短、竞争低、多核、可自旋 → 用自旋锁
* 否则 → 用 mutex，别逞强

> 知其然，更知其所以然——选型之前，先想清楚场景，再跑一遍基准。
